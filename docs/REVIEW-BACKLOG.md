# کارهای باقی‌مانده: Skills & Rules و موتور ریویو

فهرست کارهایی که بعد از نسخهٔ 0.6.2 مانده‌اند. هر مورد طوری نوشته شده که بدون تاریخچهٔ گفتگو هم قابل اجرا باشد.

برای شروع کار کافی است بگویید مثلاً: «مورد ۲ از `docs/REVIEW-BACKLOG.md` را انجام بده».

**قبل از شروع:** شماره خط‌ها مربوط به زمان نوشتن هر مورد هستند و ممکن است جابه‌جا شده باشند؛ کد فعلی را دوباره چک کنید. قوانین نسخه، Changelog و مستندات دوزبانه در `AGENTS.md` هم برای این کارها لازم است. بعد از انجام هر مورد، آن را از این فایل حذف کنید.

## اولویت بالا

### ۲. وصل‌کردن تب Skills & Rules به موتور (فاز ۳)
**مشکل:** `apps/web/src/SkillsView.tsx` همه‌چیز را فقط در `localStorage` نگه می‌دارد و هیچ‌چیز به سرور نمی‌رسد.
- ویرایش و حذف Skill هیچ اثری روی ریویو ندارد و Skill پیش‌فرضِ حذف‌شده بعد از رفرش برمی‌گردد.
- متن صفحه ادعای مسیردهی خودکار دارد که وجود ندارد.
- `Dead Code Analyzer` نمایش داده می‌شود ولی وجود ندارد. `Contributing Reviewer` اجرا می‌شود ولی در فهرست نیست.
- از ۳۲ Rule فعال فقط یکی نشان داده می‌شود.
- چک‌لیست‌ها حالا در `SPECIALISTS` داخل `packages/shared/src/agents.ts` هستند و نسخهٔ UI از آن‌ها جدا مانده است.

**پیشنهاد:**
1. یک API که فهرست واقعی Agentها و Ruleها را از `SPECIALISTS` و `DEFAULT_RULES` برمی‌گرداند. فهرست ثابت `DEFAULT_SKILLS` از UI حذف شود.
2. برای هر پروژه: روشن و خاموش کردن Agent و Rule، به‌علاوهٔ متن اضافه برای هر Agent. می‌تواند روی `suppressedRules` و دستورالعمل‌های پروژه بنا شود.
3. ساخت Agent کاملاً سفارشی مرحلهٔ جداگانه‌ای باشد.

**نکته:** Ruleهای امنیتی نباید برای کل پروژه خاموش شوند؛ همان محدودیت `SECURITY_RULE_IDS` در `apps/api/src/handlers/projects.ts` باید سمت سرور رعایت شود. حذف فهرست قدیمی ممکن است `localStorage` کاربران را بی‌مصرف کند که اشکالی ندارد.

### ۱۲. یافته‌های تکراری بین دسته‌های مختلف
**مشکل:** `groupKey` در `packages/orchestrator/src/critic.ts` دسته را هم در کلید دارد، پس یک مشکل با دسته‌های متفاوت هیچ‌وقت ادغام نمی‌شود. مثلاً در اندازه‌گیری 0.6.2 نشت `BufferedReader` سه بار با دسته‌های `performance`، `resource-management` و `security` گزارش شد. Agentها دسته را آزادانه می‌نویسند.

**کار:** مقایسه را روی همان فایل و خط و بین دسته‌ها انجام دهید و فقط با شواهد (عنوان یکسان یا شباهت کافی) ادغام کنید. دسته‌بندی مجاز خروجی Agentها را هم محدود کنید. نتیجه را با `eval:live` بسنجید، چون Recall نباید کم شود.

### ۱۳. رفتار در برابر خطای 429
**مشکل:** کلید AvalAI محدودیت ۵۰ درخواست در دقیقه دارد. هنگام رسیدن به این سقف، Agentها فوری شکست می‌خورند و `Retry-After` یا `x-ratelimit-reset-requests` رعایت نمی‌شود. در ریویوی واقعی هم ممکن است بخشی از متخصص‌ها اجرا نشوند.

**کار:** برای 429 با توجه به زمان اعلام‌شده در header دوباره تلاش کنید و تعداد درخواست هم‌زمان را محدود کنید. بررسی کنید که UI شکست متخصص‌ها را واضح نشان می‌دهد و ریویو را «تمیز» جلوه نمی‌دهد.

## اولویت متوسط

### ۳. فیدبک ردشده داخل بلوک مورداعتماد پرامپت
**مشکل:** `getFeedbackDigest` در `apps/api/src/project-store.ts` عنوان و دلیل یافته‌های ردشده را به دستورالعمل پروژه اضافه می‌کند و این متن داخل `<project_guidelines>` می‌رود که برای مدل مورداعتماد است. عنوان و دلیل از خروجی مدل روی MR می‌آیند، پس این یک مسیر غیرمستقیم تزریق پرامپت است. این مسیر فقط از روی کد دیده شده و عملاً امتحان نشده است.

**کار:** digest را از `project_guidelines` جدا کنید و داخل `untrustedBlock` بفرستید. دستور مربوطه در `UNTRUSTED_INPUT_RULES` هم باید به‌روز شود. این متن باید در پیام نهایی بماند تا پیشوند مشترک کش تغییر نکند.

### ۴. زبان پیام Ruleها
**مشکل:** بیشتر پیام‌ها در `packages/config/src/rules.ts` انگلیسی‌اند، دو پیام (`no-alert` و `governance.require-release-change`) ثابت فارسی‌اند و `AI_REVIEW_COMMENT_LANGUAGE` روی هیچ‌کدام اثر ندارد. پس گزارش مخلوط می‌شود.

**کار:** پیام‌ها را بر اساس `ruleId` به فارسی و انگلیسی ترجمه کنید و زبان را از `resolveCommentLanguage` بگیرید. برای زبان‌های دیگر انگلیسی بماند.

### ۵. هزینهٔ مدل بدون قیمت
**مشکل:** در `runAgent` داخل `packages/orchestrator/src/executor.ts` اگر مدل در جدول قیمت نباشد، `costUsd` صفر می‌شود. پس سقف دلاری بودجه برای آن مدل عملاً مصرف نمی‌شود و گزارش هزینه هم صفر است. در اندازه‌گیری 0.6.2 این موضوع برای `gpt-5.6-luna` روی AvalAI هم دیده شد: این مدل در جدول قیمت نیست.

**کار:** در گزارش مشخص شود که قیمت نامعلوم است، و برای بودجه یک نرخ محافظه‌کارانه استفاده شود.

### ۶. اجرای Contributing Reviewer بدون دستورالعمل
**مشکل:** این متخصص در `planner.ts` همیشه اجرا می‌شود، حتی وقتی پروژه هیچ دستورالعملی ندارد و پرامپتش می‌گوید در این حالت قانونی تحمیل نکن. احتمالاً یک تماس LLM هدر می‌رود.

**کار:** وقتی دستورالعمل پروژه خالی است آن را اجرا نکنید. `plan()` باید این اطلاع را بگیرد. قبلش بررسی کنید چک‌های عمومی مثل کامل بودن PR template از دست نرود.

### ۷. نبود Rule برای `exec` در JS
**وضعیت:** در 0.6.0 گزارش `exec(` در JS به‌عنوان `eval` حذف شد، چون پیامش غلط بود. الان Rule قطعی برای `child_process.exec` با ورودی پویا نداریم و این کار فقط به Security Reviewer سپرده شده است.

**کار:** یک Rule جدا با پیام درست اضافه کنید که فقط وقتی فعال شود که `child_process` در همان diff import شده یا `exec` ورودی پویا دارد.

### ۱۴. گسترش دیتاست eval با MR واقعی
**وضعیت:** `packages/eval/datasets/synthetic/v2/` فقط ۱۱ نمونهٔ ساختگی دارد. بعضی FPها مشکل واقعی‌ای هستند که در دیتاست ثبت نشده است (مثلاً `AttributeError` برای کاربر بدون سفارش در نمونهٔ `v2-03`)، پس Precision گزارش‌شده پایین‌تر از مقدار واقعی است.

**کار:** چند MR واقعی اضافه کنید و یافته‌های درستِ اضافه را در `expectedFindings` ثبت کنید. اجرا روی کلیدهای دارای محدودیت: `npm run eval:live -- --pace-ms 15000 --output eval.json`، و برای تطبیق کلیدواژه‌ها `AI_REVIEW_COMMENT_LANGUAGE=en`.

## اولویت پایین

### ۸. متن نادرست How It Works
`apps/web/src/HowItWorksView.tsx` (حدود خط ۳۶ تا ۵۲) می‌گوید `docs/contributing` و `.eslintrc` خوانده می‌شوند و نام برنچ همیشه چک می‌شود. در واقع هیچ‌کدام خوانده نمی‌شوند و بررسی برنچ فقط با `AI_REVIEW_GOVERNANCE_RULES=1` فعال است. متن باید با رفتار واقعی یکی شود.

### ۹. نسخهٔ ثابت در نوار کناری
`apps/web/src/App.tsx:140` مقدار `v0.2.0` را ثابت نوشته است. نسخه را هنگام build از `package.json` ریشه بگیرید (مثلاً با `define` در `apps/web/vite.config.ts`).

### ۱۰. تازه‌شدن فهرست Ruleهای خاموش
بعد از خاموش‌کردن Rule از صفحهٔ ریویو، فهرست صفحهٔ پروژه تا باز شدن دوبارهٔ پروژه تازه نمی‌شود. `onRulesUpdated` در `PublishIssueCard.tsx` فقط `customInstructions` را منتقل می‌کند.

### ۱۱. تمیزکاری
- `coveredCategories` در `planner.ts` را هیچ‌کس پاس نمی‌دهد و کد مرده است. اگر زنده شود خطرناک است، چون یک یافتهٔ Rule کل Security Reviewer را رد می‌کند. بهتر است حذف شود، همراه با ادعای مشابه در کامنت‌های `packages/config/src/engine.ts` و `rules.ts`.
- `RULE_ENGINE_PRODUCER` در `apps/api/src/handlers/projects.ts` کپی محلی `RULE_ENGINE_AGENT` است. بهتر است از `@ai-review/orchestrator` export و همان استفاده شود.
- `tsc -p tsconfig.json` در ریشه خطاهای قدیمی `Result.error` نشان می‌دهد (مثلاً `publish.ts` و `test-provider.ts`). typecheck رسمی پروژه (`npm run lint`) پاس است؛ یا این tsconfig اصلاح شود یا مشخص شود که استفاده نمی‌شود.
